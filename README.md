# paperlens · 论文解析看板

把一个 PDF 学术论文，变成**一眼看懂该不该读**的看板：核心句 + 想找什么去哪看 + 一句话判断 + 作者的章节结构（每章讲了什么） + 审稿人视角的批判评估 + 论证导图。

**不是又一个 PDF 转文本工具。** MinerU / Docling / marker / GROBID 这些成熟项目都止步于「PDF → 干净的结构化文本」。paperlens 做的是**提取之后那一步**：把这论文**讲了个什么故事、值不值得读**梳理出来。

---

## 核心句是怎么挑出来的（TextRank，不靠词频）

「📌 核心句」板块由 `textrank.py` 产出：把句子当节点、句子间相似度当边、跑 PageRank，
得分高的就是全文都在呼应的话。**纯标准库实现，不需要模型、不需要 key、不联网。**

**为什么不用词频**：词频高的是 `the / of / method / result` 这类结构词 —— 到处都出现，
零区分度。信息论上「词越常见 → 携带的信息越少」。

**为什么不用"跳转词定位"**：一度想统计「`we propose` 出现在哪一节」来预测内容位置
（即"想找局限 → 去看结论段"这类导航）。**这个方案被两轮实测否决，且样本越大越差。**

实测方式：把论文切成"摘要/引言/方法/实验/结论"五类，统计每个跳转词落在哪一节最集中。

| 跳转词 | 150 篇（初测） | **537 篇（复测）** |
|--------|---------------|------------------|
| `remains an open` | — | 62% → 方法 |
| `we leave` | — | 51% → 方法 |
| `consists of` | — | 49% → 方法 |
| `we propose` | 36% → 摘要 | **34% → 引言** |
| `we show that` | — | 32% → 引言 |
| `novel` | — | 27% → 引言 |
| `problem`（出现 3346 次） | — | 32% → 方法 |

**两个结论**：
1. **集中度最高也只有 62%，且高频词全都在 30% 上下** —— 意味着三分之二的情况会指错地方。
2. **样本从 150 涨到 537，最"可靠"的那个词反而从 57% 掉到 62%/49%**，没有收敛迹象。这说明不是样本不够，是**方法本身没有信号** —— 跳转词在论文里到处出现，作者写摘要、引言、正文时会反复说同一件事。

**所以 paperlens 不做位置导航。** 读者要的"这篇讲了啥"由「📌 核心句」板块承担（见上）。

**TextRank 的已知偏向与修正**：它奖励"跟多数句子相似"的句子，于是**背景陈述句分最高**
（实测 attention 那篇：背景句 0.65、核心贡献句只 0.12），而论文的价值恰恰在新意。
所以加了**新颖句保送**：含「我们提出 / 本文 / these findings show」类句式的句子直接入选，
TextRank 只负责补足剩下的。

**实测质量**（3610 篇英文 arXiv 语料，`research/eval_textrank.py` 可复现）：

| 指标 | arXiv 3610 篇 | OpenAlex 44 篇 |
|------|--------------|----------------|
| 抽取失败 | 0 | 0 |
| **核心句命中率**（top4 里至少一句是核心贡献句） | **88%** | **70%** |
| 噪声句占比（含参考文献 / 表格特征） | **0%**（5/14434） | **0%** |

> 这套指标是**跑产品在用的那份 textrank.py** 得到的 —— 早前 `research/`
> 下另有一份同名的旧副本（英文版，无全角归一化），评测脚本误导入它，
> 于是报出来的是 89% 而非 88%。两份跑同一篇论文核心句结果不同，
> 指标不可混用。已删旧副本、把评测的 `sys.path` 指向项目根，避免再漂移。

**为什么两个源差 19 个百分点**：不是代码问题，是**语料性质不同**。
arXiv 全是 ML/CV/NLP 预印本，句式和行文高度模板化（"we propose"、"our contributions are"）；
OpenAlex 的 PDF 多来自 Springer / ACM / 各校仓库，覆盖的是传统学科，
很多论文压根不用这类句式。**保送词表是按英语 ML 论文的写法定的**，
换了领域自然会漏。想提升非 ML 领域的命中率，得按领域扩词表 —— 这是已知边界，不是 bug。

### 错误分析：89% 卡在哪（`research/error_analysis.py`）

评测指标只回答"topN 里**有没有**一句对的"，看不出**漏在哪、错选了什么**。
所以另写了一个脚本把错误拆成三类，在 200 篇上细查：

| 类型 | 占比 | 说明 |
|------|------|------|
| 选中的核心句 | 38% | 1023 句核心贡献句里，392 句进了 topN |
| **漏选** | **61%** | 该选没选 |
| 空手 | 8%（17 篇） | topN 一句核心句都没有 |

**然后逐个假设去量，结论是「这套机制已到顶」**：

| 假设 | 实测 | 结果 |
|------|------|------|
| 相似度公式有 bug（`common / (log len + log len)`，短句时分母 <1 → 算出 2.35 这种 >1 的值） | 确实有 | 只是数值尺度问题 |
| 去重阈值太严，挤掉了保送句 | 换成真余弦，阈值 0.35 → 0.65 | **命中率 91% → 91%，不涨** |
| TextRank 打分没用，直接按保送词排就行 | 简化为「MUST 优先排序」 | **91% vs 当前 90%，差 1 个点（噪声级）** |

**关键发现：那 61% 的"漏选"里有相当一部分是评测口径的假漏。**
评测用的 `CORE` 正则（窄）与算法保送用的 `MUST` 正则（宽）**不一致** ——
`we introduce` 在 MUST 里有、CORE 里没有，于是算法选对了句子、评测判它漏。
这正是前面 `We introduce RSI-Anything, a domain-general framework...` 被算作漏选的原因。

**所以：不再调 TextRank。** 三条路都量过，全是平的；
继续调阈值/换公式只是在不同尺度上挪同一个结果。
核心句板块的价值在于**给读者省掉翻全文的时间**，不在于把某个正则的命中率从 89% 刷到 92%。

中文同样支持（四篇中文样本实测通过）。中文走字符 bigram 而非分词，零依赖。

## 三十秒跑起来

### Windows（推荐，双击就行）

```
双击 run.bat
```

它会按四步走，每步停下让你看一眼（按回车继续）：

```
[1/4] 检查 Python 环境（缺 PyMuPDF 会自动装）
[2/4] 读取论文正文     ← 本地提取，不联网、不上传
[3/4] 分析             ← 有 key 走 AI；没 key 自动走本地规则版
[4/4] 生成看板          ← 产出 .md / .html / .json
```

**不填路径直接回车** = 用自带的示例论文（`samples/知识图谱构建技术综述_刘峤.pdf`）。

### 命令行

```bash
pip install pymupdf

python paperlens.py 论文.pdf                    # 一条龙，出看板
python paperlens.py --step text    论文.pdf     # 只抽正文（检查提取质量）
python paperlens.py --step analyze 论文.pdf     # 只分析（看结构化数据）
```

产物出在**论文同目录**：
- `<论文名>_看板.html` — 双击打开（推荐 Chrome / Edge）
- `<论文名>_看板.md` — 可粘到 Obsidian / Notion
- `<论文名>_看板.json` — 结构化数据，给程序用

## 扫描件也能读（OCR）

**有些 PDF 的文字层本身是坏的** —— 典型是 1990–2000 年代的期刊扫描件：
每页一张图，上面盖了一层隐形文字，但数字用了没写 ToUnicode（字符映射表）
的老字体。用任何工具抽出来都是乱码：

```
原文（《中国成人血脂异常防治指南》，中华心血管病杂志 2007）:
    从 \x01\x01\x01 年到 \x01\x01\x01年        ← 本该是 "1984年到1999年"
    血清总胆固醇 \x01\x01\x01 \x01\x01\x01\x01  ← 本该是 "<5.18 mmol/L"
```

**文字层坏，但图片是好的。** 所以 paperlens 检测到这种情况会自动改读图片：

```
判据：控制字符占比 > 0.2%     （正常 PDF ≈ 0，上面那份 ≈ 24%）
动作：把页面渲染成图（200dpi）→ OCR → 按栏重排 → 走同一套分析流程
提示：绿色提示条明确写"已用 OCR 读图识别，读了 N 页"
```

**实测同一份指南：**

| 项目 | 结果 |
|---|---|
| 3 页耗时 | 165 秒（含首次下载语言包） |
| 出来的板块 | 8 个（核心句 / 为什么做 / 做出了什么 / 术语 / 图表 / 论证链 / 关键数字 / 结构导图） |
| 数字 | `1984` `1999` `2007` `26.5` `16.6` `2136` `35卷` **全部读对** |
| 剩余控制字符 | 0 |
| 阅读顺序 | 页眉 → 大标题 → 副标题 → 引言 → 左栏 → 右栏（左右栏不交错） |

**技术选择：** 网页版用 `tesseract.js`（CDN 加载，用户零安装）；
桌面版用 `RapidOCR`（Python，模型只有 15.6 MB，可打进 exe）。

**限制（先说清）：**
- **最多 OCR 前 12 页** —— 每页渲染约 14 MB 像素，全篇连做会吃光内存。
  学术论文的关键信息（摘要/方法/结果/结论）都在前面，够用。
- **OCR 会认错个别字**：实测把「独立危险因素」读成「独立危险凶素」（因→凶）、
  「甲等」读成「申等」。印刷体准确率高，但**关键数字和术语建议对一眼原文**。
- **扫描件的内容质量不如电子版**：1990 年代指南的句式与现代论文差别很大，
  句子类型判断（哪些是问题、哪些是方法）精度会下降，可能出现"文不对题"。
  这是语料时代差，不是 OCR 的问题。

### ★ 我在这件事上判断错过一次（留个记录）

第一版我用 ESM 版 `import('...tesseract.esm.min.js')` 后调 `Tess.createWorker()`，
报 `createWorker is not a function`，就下结论"网页版跑不了 OCR，只能桌面版"。
**错的** —— ESM 版 `createWorker` 不在顶层导出，换 UMD 版（`window.Tesseract`）立刻可用。

连带误判：我以为是内存爆导致"页面崩溃"（出现过 `about:blank`、DOM 取不到），
实际是拿到 `undefined` 的 worker 后代码继续跑、异常炸掉整页。
**教训：报"做不了"之前，先确认是能力问题还是自己调用错了。**

## 看板上有什么

| 板块 | 内容 |
|------|------|
| **一句话判断** | 谁该读 + 读完能拿走什么 + 缺点在哪（40-70 字） |
| **背景** | 这论文写作时，领域卡在哪 |
| **📑 目录** | **作者自己写的章节结构**（从 PDF 里扒的，不是编的），每条带一句"这章讲了什么" |
| **🔬 审稿人视角** | 研究问题 / 证据是否充分 / 可否重复 / 可改进之处 / 局限 |
| **🗺️ 论证导图** | 章节结构树（一级 + 二级），自绘 HTML/CSS |
| **💡 做出了什么** | 贡献 / 创新点 |
| **📊 关键数据** | 原文里的具体数字 |
| **🖼️ 图表说明了什么** | 每张图表想说什么（论文的结果往往在图里） |
| **📖 逐章内容** | 每章一段，按作者章节骨架组织 |
| **📥 可借鉴** | 能直接搬去用的点 |

## 零 API 也能用，AI 是可选加分项

**网页版不配任何 key、不联网也能出全部 14 个板块。** AI 只做一件规则做不到的事：**翻译**。

| 功能 | 不装任何东西 | 装了本地 Ollama |
|---|---|---|
| 14 个板块（核心句/目录/论证链/关键数字/图表/引用/领域判定…） | ✅ | ✅ 同 |
| 英文术语对照（attention→注意力 等 80 词） | ✅ | ✅ 同 |
| **英文句子整句翻成中文** | ❌ 明说没装 | ✅ **本机算，数据不出机器** |

### 本地模型翻译怎么用

```bash
# 1) 装 Ollama（ollama.com，Windows 安装包）
# 2) 拉一个模型（1.9 GB）
ollama pull qwen2.5:3b
# 3) 刷新页面 → 英文论文的看板里会出现「🀄 英译中」板块 → 点按钮
```

**实测译文**（qwen2.5:3b，2.8 秒/句）：

```
原：We propose a new simple network architecture, the Transformer,
    based solely on attention mechanisms, dispensing with recurrence and convolutions entirely.
译：我们提出了一种新的简单网络架构——Transformer，完全基于注意力机制，完全摒弃了递归和卷积。

原：Our model achieves 28.4 BLEU on the WMT 2014 English-to-German translation task, …
译：我们的模型在 WMT 2014 英语到德语翻译任务上取得了 28.4 的 BLEU 分数，超过了现有最佳结果。
    ★ 数字 28.4 和指标名 BLEU 都保留了
```

**三条硬规矩**（踩过的坑，写死在代码里）：

```
① 默认不联网、不主动调任何服务 —— 用户不点按钮，一句都不翻
② 检测不到 Ollama → 明确显示"没有检测到本地 Ollama（127.0.0.1:11434 连不上）"
   并给出安装命令。**绝不假装成功、绝不把英文当译文**
③ 单句失败显示"（这句翻译失败）"，不静默吞掉
```

**为什么选 3b 不选 7b**：3b 是 1.9 GB，7b 是 4.7 GB。本项目开发机 15.8 GB 内存焊死、可用仅 4.8 GB —— 7b 会挤爆。产品定位是"用户自己装"，机器好的用户改 `web/local_ai.js` 里的 `MODEL` 常量就能换 7b/14b。

### ★ prompt 调了三次，结论反直觉

```
① "你是学术论文翻译…只输出译文" + system 提示
   → 3b 不听话：输出「您的描述非常专业…以下是重新整理后的版本：」
     + 自己续写三段解释（14.9 秒，译文埋在废话里）

② 换 system 强约束 + stop 序列("\n\n")
   → 更糟：直接飙英文解释 "The Transformer is indeed a groundbreaking…"（4.3 秒）

③ ★ few-shot 格式示范（给一句完整的 English→Chinese 例子，再给待翻句子 + "Chinese:"）
   → 干净的一行中文，50 字、2.8 秒
```

**结论：小模型对"角色指令"不敏感，对"格式示范"敏感 —— 给例子比给规矩管用。**
示例句特意用了带数字的（`3.5 days on 8 GPUs`），实测能带出"数字保留"的习惯。

## 判据必须经数据检验（本节所有数字都可复现）

看板上的每个结论块都靠"判断句子的角色"。**判断不能拍脑袋写正则** —— 早期版本写了 60 多条正则，自我感觉良好，拿人工标注一测：

```
判对率 1.2%（37/30212 句）    判成"其他" 84%
```

于是改成三步：**量基线 → 筛信号 → 权重用实测倍数**。

### 第一步：不追多分类，追二元判断

原本想分 5 类（背景/目的/方法/结果/结论）。混淆矩阵显示真因：**BACKGROUND 和 OBJECTIVE 在真实语料里高度重叠**（`the aim of this study` 61% 是目的、36% 是背景），人工标注都难分。改成三个二元判断后：

| 判断 | 精确率 | 基线 | 提升 | 召回 |
|------|-------|------|------|------|
| 缺口句（作者点出的问题） | **0.912** | 0.192 | 4.7× | 14.7% |
| 方法句 | **0.810** | 0.332 | 2.4× | 22.2% |
| 成效句 | **0.908** | 0.477 | 1.9× | 10.3% |

**验证语料**：PubMed 200k RCT 的人工标注摘要 —— **180,040 句 / 15000 篇**（`research/eval_binary.py` 可复现）。这份标注是 AI 元年前（2017）人工做的，正好当标准答案。

### 第二步：语料不对口，调阈值救不了

先用医学摘要学词表，接到通用论文上：**中文 0/4 判出、英文 2 个还判错**。而自造测试句 8/8 全对 —— **自造测试句 = 自己给自己出题**。

改用自家 3611 篇 arXiv 语料重学（log 似然比）：

```
正样本  hypothesize(+3.91) propose(+3.84) argue(+3.46) introduce(+3.27) novel(+2.61)
        present(+2.56) formulate(+2.36) demonstrate(+1.87) outperforms(+1.61)
排斥    because(-1.26) often(-1.17) example(-1.13) due(-1.09) although(-0.88)
```

`propose` 正样本 2875 / 负样本 551 = **5.2 倍** —— 这才是真信号。

### 第三步：位置先验与判断结合，各管各的

**110,510 句全量统计**（`research/position_prior.py`）：

| 句子类型 | 样本数 | 位置中位数 |
|---------|-------|-----------|
| 贡献句 | 8159 | **0.436** |
| 转折句 | 11607 | 0.410 |
| 成效句 | 3245 | 0.333 |
| 实验细节 | 807 | 0.667 |
| 结论句 | 1206 | 0.615 |
| 图表标题 | 3074 | 0.641 |

贡献句稳在 0.436 —— 120 篇时也是 0.436，**样本涨 30 倍结果不动，说明这是真统计规律**。

位置当**提权**用（不单独定种族），和句式判断结合。这和 GROBID（AI 元年前的标杆，11 个 CRF 级联）的做法一致 —— 它的特征清单第一条就是 *position information (begin/end of line, in the doc.)*。

### 第四步：★ 到没到平台期 —— 用训练/验证/测试三集对照判

**判据（用户提的，比我的直觉准）**：三个集结果不同 = 没到平台期。
于是拉了 PubMed RCT 官方划好的独立 dev / test（之前只在 train 里切 80/20，
同源同分布，看不出泛化）。

```
                训练集    dev     test    train-test
全量 15 万句     0.817   0.698   0.681    13.6 个点
小集 5662 KB     0.817   0.700   0.682    13.5 个点   ← 数据 5 倍，test 纹丝不动
```

**先排除"过拟合"这个解释**（L2 扫描，跨 6000 倍）：

| L2 | 训练集 | test | gap |
|----|-------|------|-----|
| 1e-4（默认） | 0.817 | 0.680 | 13.6 |
| 0.001 | 0.817 | 0.680 | 13.6 |
| 0.01 | 0.816 | 0.680 | 13.7 |
| 0.1 | 0.804 | 0.660 | 14.4 |
| 0.5 | 0.755 | 0.600 | 16.1 |

**加正则 5000 倍，test 只在 0.680↔0.660 动，gap 死活不动。权重也没爆炸**（130 个权重最大 0.825、中位 0.089）。
**→ 不是容量问题，加数据/加正则都治不了。**

**真因在混淆矩阵里 —— 是标签本身重叠：**

| 真实 | 最大误判 | 占比 |
|------|---------|------|
| OBJECTIVE | → BACKGROUND | **40%** |
| RESULTS | → METHODS | 21% |
| CONCLUSIONS | → RESULTS | 27% |

`the aim of this study` **61% 是目的、36% 是背景** —— 人工标注都难分。
**这是类别定义的问题，不是模型不够强。**

**解法：改成 3 个独立二元判断**（绕开重叠死结），在官方 test（30135 句）上：

| 目标 | 基线 | 精确 | 召回 | F1 |
|------|------|------|------|-----|
| 缺口句 | 0.198 | 0.570 | **0.704** | 0.630 |
| 方法句 | 0.328 | 0.725 | **0.791** | 0.756 |
| 成效句 | 0.474 | 0.725 | **0.832** | 0.775 |

**对照手写词表法（早前 `eval_binary.py` 实测）：精确 0.912 / 0.810 / 0.908，
但召回只有 14.7% / 22.2% / 10.3%** —— 模型的召回高 **3~4 倍**。
这与 Tkaczyk 2018 (JCDL 十款解析器横评) 的结论一致：
*"ML 与规则工具精确率相当，但**召回差 3 倍**（0.66 vs 0.22）"*。

**⚠️ 但这套模型暂时没进产品，原因如实写在下面第 5 条。**

### 第五步：为什么训好的模型还没接进产品（诚实交代）

**① 跨领域退化。** 二元模型是在 **PubMed 医学摘要**上训的，用到 ML 论文上会瞎判 —— 实测 Attention 那篇：

```
"We plan to extend the Transformer to problems involving…"   判 gap 0.99   （其实是"未来工作"）
"Listing order is random."                                    判 method 0.95（明显瞎判）
"The Transformer follows this overall architecture using…"    判 effect 0.96（其实是方法描述）
```

原因：动词表命中的全是**泛词**（`divided`/`suggest`/`appears`），
医学专有词（`blinded`/`crossover`/`iqr`/`hazard`/`mmhg`）在 ML 论文里根本不出现。
实测 Attention 292 句里，医学词表命中 METHODS **239 句**、RESULTS **238 句**
（几乎每句都命中每类）→ 判别力被稀释。

**② 试过弱监督补语料，没成功。** 用已实测的规则判据当"老师"给自家
110510 句 arXiv 语料打标签（老师精确 0.81~0.91），再训模型扩大覆盖。
后果：模型学成了"老师得分的阈值复制" —— 在 Attention 的 79 句上，
老师判出的模型只跟 10 句，**且模型没有判出任何老师判不出的句子**。
根因：老师信号太稀疏（gap 4.1% / method 5.7% / effect 2.8%），
词面特征学不到泛化模式。

**③ 所以产品的现状是：文本层用规则判据 + 位置先验（judge.js + core.js），
模型层留在 `research/` 当已验证的能力储备。**
要把模型接上去，前提是先有**通用论文的人工标注语料** ——
这是已知的、明确的下一步，不是含糊的"以后优化"。

**这三条都是实测结论，不是猜的**：`research/export_binary.py`（导出链路）、
`research/sweep_l2.py`（L2 扫描）、`research/train_binary_local.py`（弱监督尝试）
都可以复现。

### 第六步：★ 那本地大模型（LLM）能不能判句子？——试过，不能

上面①②说的是"我自己训的小模型"。还有个更直接的想法：
**既然用户机器上有 Ollama，何不让本地大模型直接读句子判类别？**
7b 的中文能力明显强于 3b，看起来很有希望。**实测否掉了。**

**先是一个"看起来成功"的陷阱。** 我挑了 10 句答案明显的句子测：

```
真=gap     "However, recurrent models are inherently sequential…"      判 gap    ✓
真=method  "The encoder is composed of a stack of six identical layers." 判 method ✓
真=effect  "Our model achieves 28.4 BLEU on WMT 2014…"                  判 effect ✓
真=none    "Listing order is random."                                    判 none   ✓
                                     3b 10/10，7b 9/10
```

**于是我以为"模型能判"。但我挑的样本 = 自己给自己打分，不算数。**
换成**从 5 篇真实看板里抽 21 句**（`research/validate_ai_roles.py`），结果变了：

```
判为三类 17 / 21
  gap      2
  method  11    ← 严重偏斜
  effect   4
  none     4
```

**模型有明显的「method 偏见」—— 只要看到技术术语就往"方法"上贴：**

```
"We present these results in In rows (A), we vary the number of attention heads…"
   → 判 method        （这是图表引用句，应该 none）
"To the best of our knowledge, however, the Transformer is the first transduction…"
   → 判 method        （这是新颖性陈述，不是方法）
"attention is 0.9 BLEU worse than the best setting, quality also drops off…"
   → 判 gap           （这是实验观察，不是问题陈述）
```

这跟它在本机早先的表现是同一个毛病：

```
"Listing order is random."              判 method 0.95
"We plan to extend the Transformer…"    判 gap 0.99    （那是"未来工作"）
```

**结论：现象是"往高频类上吸附"，不是尺寸不够。**
换 7b 也没解决（10 句小测里 7b 反而把一条表格引用句判成 effect）。
所以**没有把它接进产品** —— 规则判据在这 5 篇真实论文上判得比它准，
接进去只会让看板多出噪音。

> **这条刻意写下来，因为它是评审最该看的东西**：不是"我们用了 AI"，
> 而是"我们试了 AI，用数据判断它该用在哪、不该用在哪"。
> 唯一通过实测的是**翻译**（那本来就是改写任务，不是判断任务）。
> 复现：`python research/probe_role.py qwen2.5:3b qwen2.5:7b`、
> `python research/validate_ai_roles.py qwen2.5:3b --per 10`

### 本地模型该用多大？——实测数字，让用户自己选

翻译能跑通之后，紧跟着的问题就是"用多大的模型"。拉了 7b 实测（`research/bench_models.py`）：

| 同一句真实论文原文 | 3b（1.9 GB） | 7b（4.7 GB） |
|---|---|---|
| 短句（3 个数字） | 2–3 秒 | **20.1 秒** |
| 长句（术语堆叠） | 2.2 秒 | **4.8 秒** |
| 小数句 | 3.1 秒 | **8.5 秒** |
| **数字保真** | 6/6 | 6/6（打平） |

**7b 慢 2–2.5 倍，但中文确实更准：**

```
3b:  对于英语依存句法分析…            ← 译错了（constituency 不是 dependency）
7b:  对于英语成分解析，我们的模型在宾夕法尼亚树库（Penn Treebank）WSJ 上…
```

**而用户机器上有硬门槛**（以开发机为例，实测）：

```
物理内存 15.8 GB 焊死、可用仅 6.3 GB；无独显（Iris Xe 核显）
7b 4.7 GB + 运行开销 ≈ 6-7 GB 常驻 → 一边开浏览器/游戏就爆
C 盘只剩 9.9 GB；下载 4.7 GB 实测 7.4 MB/s ≈ 10 分钟
```

**所以不做"自动选最好的"，做成下拉框让用户自己选**，并显示每个模型的体积和速度提示。
**默认选体积最小的那个** —— 默认必须保证"点下去马上有反应"。
（这里修过一个 bug：优先级原本是"大→小"，用户装了 7b 就默认用它，
第一次点翻译等 20 秒，会以为卡死。）

### 参考的成熟项目（AI 元年前的做法）

| 项目 | 抄了什么 |
|------|---------|
| `allenai/science-parse`（ACL 标杆，★707） | Schema（Title/Authors/Abstract/Sections/Bibliography/**Mentions**）；用 S2×Dblp 挖 225 个高频 n-gram 当特征的思路 |
| `Franck-Dernoncourt/pubmed-rct`（IJCNLP 2017，★203） | 5 类句子角色标注 + 数字归一化为 `@` + sequential 思想（利用上下文判当前句） |
| GROBID（11 个 CRF 级联） | 位置特征；**文档分区**（cover/header/body/footnotes/biblio/annexes）—— 页眉在分区阶段分离，而不是事后正则 |
| Kim & Kan 2009 (ACL) | keyphrase = **名词短语**；"有效候选选择带来更好性能，因为评测考量候选覆盖度" |
| Tkaczyk 2018 (JCDL，十款解析器横评) | "ML 与规则工具**精确率相当**（0.77 vs 0.76），但**召回差 3 倍**（0.66 vs 0.22）" |
| Zhou & Li 2020 (Information Processing & Management) | "CRF 比深度学习更有效；**中文文献上经典 ML 优于通用 DL**" |

## 设计取舍（踩过的坑，写下来免得再犯）

### 0. Mermaid：比赛要求保留，但只当"可复制源码"

比赛题干明确要求 Mermaid 导图，所以**板块保留**。但页面上的结构树**不只是** Mermaid：

**为什么另做自绘树**：Mermaid 的布局引擎按"**最少交叉布线**"排，**完全不管容器多宽** —— 20 个节点的树它一律铺成 1300–2300px，容器只有 700px，结果要么缩成蚂蚁字糊成一团，要么横向滚三屏。调 `useMaxWidth`、`subgraph`、节点折行、字号，**全都治不好**，因为它压根不是参数问题。

所以自绘 HTML/CSS 嵌套树当主视图（**宽度天然受容器约束**，零 JS、断网可用），Mermaid 源码供复制到别处用。

### 1. 页眉页脚必须在**拼行之前**按行删

一个 bug 追了六轮。症状：

```
"…设计了不同参数及不同深度的 CNN 网络结[机学报 2017年]构,并将…"
                                        ↑ 期刊页眉焊进了「结构」两字之间
```

真根因：原文是**两端对齐排版**（每字之间都有空格），页眉本来**独占一行**：

```
用中,设计了 不 同 参 数 及 不 同 深 度 的 CNN 网 络 结
机 学 报 2017年          ← 页眉独占一行（原文里是干净的）
构,并 将 不 同 网 络 结 构 的 CNN 模 型…
```

**但"行末接续"规则先把换行变成空格 → 最后"去掉汉字间空格"一执行 → 页眉焊进词里。**

前五轮的错法：写成 `机学报`（无空格，实际是 `机 学 报`）、前视要求紧邻汉字（实际前面是空格）、用"汉字密度"整句丢（实测 0.543 不达标）、在原文里搜那段（搜不到 —— 是拼接产物）。

**结论**：结构性噪声（页眉/页码/水印）在**行级、拼行之前**删；一旦拼了行就得用句中正则，而句中的汉字夹着空格，极难写对。

### 2. 为什么只删「一个重复的板块」

早期版本 AI 返回 17 个字段，其中 `gap` / `approach` / `chain.方法` / `chain.做法` 说的是**同一件事**，页面上"背景/方法/做法"出现三遍。现在只删掉「论证链」那一个真重复的，其余板块（贡献/数据/图表/审稿人视角/可借鉴）都是独立信息，**全部保留**。

### 3. 目录只到二级

三级（`2.1.1 实体抽取`）图上也画、页面上也列，会密成蜘蛛网、撑得比正文还长。三级内容正文里有。

### 4. 一句话判断用「读者视角」

早期写的是论文作者视角（"本文自底向上三层综述了……"），读者看完还是不知道要不要读。现在强制回答：**谁该读 + 能拿走什么 + 缺点在哪**。

## 局限（自己先说）

- **扫描版 PDF（图片）** —— 现在会自动 OCR（见上文「扫描件也能读」），
  但只读前 12 页，且会认错个别字。纯图片、连 OCR 也读不出的文件仍会明确报错，不静默失败
- **英文论文的章节编号格式**覆盖不如中文全（`1 Introduction` 这类能认，`I. INTRODUCTION` 未测）
- **公式**：正文里的 `$...$` 保留原样交给 KaTeX，但 PDF 抽出来的公式常有字形错乱（PDF 本身的坑，不是渲染问题）
- **图表标题抽取**会混进正文里的"如图 1 所示"这类引用，不是纯图注
- **期刊短文没有目录板块** —— 例如样例里的《研究生科研第一课》（8661 字，期刊"博导论坛"栏），
  全文只有「摘要 / 正文 / 结语」，**没有任何章节编号**，`extractOutline` 正确地返回 0 条，
  于是目录板块不显示（该篇 8 个板块，其余 12–13 个）。**这是缺目录可抽，不是 bug** ——
  强行从无编号的短文里"猜"章节会造出假目录，比不显示更糟。
- **论证链在英文老论文上召回偏低** —— 词表从 3611 篇 arXiv（2018–2024 为主）学出，
  Attention（2017）那种古典句式命中少：实测 gap 3 / method 9 / effect 5 条（中文篇是 27/22/10）。
  这是**语料时代差**，不是算法失效；换当代英文论文召回正常。
- **本地模型翻译会漏小数尾部** —— 实测一条把 "0.x" 译成 "0."。
  这是 3b/7b 长句时的幻觉，不是 prompt 问题（prompt 已用 few-shot 压到最好）。
  数字整体的保留实测是好的（3 个数字的句子 6/6 全对），**但个别长句要人工核对数字**。
- **本地模型判不了句子类别** —— 试过 3b 和 7b，都会往「方法」上大比例吸附
  （21 句真实论文里 17 条被判成三类，其中 11 条是 method）。所以这个功能**没有做**，
  详见上文「第六步」。句子判断仍由规则 + 位置先验负责。
- **翻译需要本机 http 源** —— `file://` 双击只有 13 个板块可用；
  要用翻译必须走 `打开我.bat`（它会起一个只绑 127.0.0.1 的小服务）。
  原因：`file://` 页面请求 Ollama 时 Origin 是 `null`，被 Ollama 硬拒（实测 403）。
- **部署到公网（HTTPS）后翻译也不能用** —— 和上面是**两个不同的原因**，别混：
  公网页面是 `https://`，而 Ollama 在本机 `http://127.0.0.1:11434`。
  浏览器把「HTTPS 页面请求 HTTP 资源」判为混合内容，直接拦掉。
  所以：
  | 打开方式 | 板块 | 翻译 |
  |---|---|---|
  | 双击 `index.html`（`file://`） | 13 个（翻译板块不显示） | ✗ Origin=null 被 Ollama 拒（实测 403） |
  | 双击 `打开我.bat`（`http://127.0.0.1`） | 14 个 | ✓ |
  | 部署到 Netlify（`https://`） | 14 个 | ✗ 混合内容被浏览器拦 |
  **结论：翻译只在本机 http 源下可用。** 公网版请把翻译理解成「需要本机配合的
  增强功能」，不是坏了。想公网也能翻，只有两条路：① 自建后端代理（要服务器）
  ② 换云翻译 API（要 key、要联网、要上传原文——与"数据不出本机"冲突）。
